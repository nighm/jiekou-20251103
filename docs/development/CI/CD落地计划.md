# CI/CD 落地计划

## 1. 背景与目标
- 本项目目前尚未配置 CI/CD 流程，所有测试与质量检查依赖人工执行，缺乏可重复的自动化保障。
- 仓库已具备 `pytest`、`tox`、`ruff`、`mypy`、`pip-audit` 等工具配置，可作为流水线基础。
- 目标是在不额外引入复杂度的前提下，分阶段完成 CI/CD 落地：先梳理文档、再上线基础 CI、逐步扩展质量保障，最终为持续交付预研奠定基础。

## 2. 实施原则
- **文档优先**：任何改动须以最新文档为准，先对现有文档做梳理与整合。
- **复用现有能力**：优先使用项目中已配置的脚本、依赖分组和工具，避免重复建设。
- **最小可行增量**：每个阶段都保证可独立落地和回滚，避免一次性大改动。
- **质量门禁**：CI 阶段必须覆盖单元测试与静态检查，确保主干代码稳定。
- **可追溯性**：所有产出（报告、日志、制品）统一归档，便于审计与回溯。

#### 示例结果目录建设方案
- **目录位置**：位于 `result/jmeter/sample_reports`，符合项目制品统一归档规则。
- **内容要求**：
  - 包含最小化 JMeter 输出样例（如单个 `.jtl`、生成的 HTML 报告片段、关键日志），需来源于实际可复现的测试计划，不得伪造数据。
  - 提供 `README.md` 说明文件，描述数据来源、生成命令（参考 `python -m jmeter_test_suite report --input <样例目录>`）以及流水线上传策略。
- **生成流程**：
  1. 使用现有的 CLI `python -m jmeter_test_suite run` 在本地生成一次基础数据（可通过配置文件控制最小负载）。
  2. 将产出的必要文件复制到 `result/jmeter/sample_reports`，并在文档中记录生成日期与对应配置快照。
  3. 在 Gitee Go 流水线中通过缓存机制保护该目录，构建结束后作为制品打包输出。
- **维护策略**：若后续测试脚本或默认配置更新，需同步刷新样例数据并记录版本号，避免文档与制品脱节。

#### 日志输出优化规范
- **覆盖范围**：依赖安装、单元测试、静态检查、报告生成与制品上传步骤均需增加明确的提示与失败原因说明。
- **示例**：
  - `echo "📦 正在安装项目依赖（pip install -e .[dev]"`
  - `echo "✅ pytest 执行通过"` 或 `echo "❌ pytest 执行失败，请检查 tests 目录下的日志"`
- **实施步骤**：
  1. 在 `ci_basic.yaml` 中为各步骤添加成对的开始/结束日志，确保日志能在流水线界面搜索。
  2. 对错误输出添加 `set -e` + 自定义提示，或在失败时附带简短排查建议。
  3. 在 `README.md` CI 章节中同步示例日志片段，方便研发理解触发效果。
- **验收标准**：
  - 主分支提交触发流水线，四项质量检查全部通过，失败时中断并回显日志。
  - 流水线产出包含执行日志、测试报告，存放于 Gitee Go 制品区。
  - 文档中注明流水线触发条件、质量门禁覆盖范围与下一阶段展望。
